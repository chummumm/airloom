# Airloom 架构

Airloom 是从零实现的 Windows 桌面项目。它使用 Windows 自带的 WASAPI 采集已有输出端点，使用独立实现的 AirPlay 发送器发送音频，原生界面使用 WinUI 3 / C++/WinRT。它不安装自定义声卡驱动，也不会新增系统播放设备。

## 三个模块

| 模块 | 负责的内容 | 不向上层暴露的细节 |
| --- | --- | --- |
| `airloom-capture` | 已有音频端点枚举、采集、格式转换、重采样、可选本机静音、凭据存储 | COM 生命周期、WASAPI 缓冲区、设备格式、线程归属 |
| `airloom-airplay` | mDNS 发现、认证、RTSP 控制、音频编码与发送、时钟与重传 | SRP/TLV/加密帧、协议序列、网络包 |
| `airloom-core` | 用户选择、连接状态、取消、恢复、可观测指标 | 网络与音频模块之间的调度、密码生命周期 |

`native/Airloom` 是真正的 WinUI 3 应用。它通过一个很小的 UTF-8 JSON C ABI 与 `airloom_core.dll` 交换命令和快照；GUI 线程不执行网络连接或音频采集。ABI 见 [`include/airloom.h`](../include/airloom.h)。

## 声音与时序

Windows 采集在线程内部转换成 44.1 kHz 双声道浮点 PCM。核心把它量化成 16-bit PCM 后交给发送器。采集队列有界；发送拥塞不能导致无限堆积，恢复连接时不能播放数秒前的陈旧音频。UI 的波形和左右声道电平来自真实 PCM；空闲状态为平线。

声音捕获只涵盖已有端点的共享模式播放。当前界面只展示已实现的端点源，不把未实现的进程采集作为可选项。WASAPI loopback 不等于路由：采集不会自动移除本机声音。静音是用户可选操作，不默认开启；具体端点的静音前采集行为必须实机验证。

## 连接与密码

连接状态明确区分空闲、发现、连接中、等待认证、发送中、重连和错误。只有发送器完成会话建立并启动音频采集后，才进入发送状态。它表示发送链路已建立，不是设备已经发出可听声音的测量结果。

设备密码、配对码和长期配对凭据是不同的数据。认证模块根据接收端响应处理；凭据失败返回认证界面，不能无限自动重试。密码不进入快照、错误诊断、日志或仓库。只有用户勾选“在此电脑记住”时，才持久化到 Windows 当前用户的凭据存储。忘记设备会删除已存凭据。

## 静音恢复与退出

捕获模块记录自己设置的端点静音变更，监听外部修改。停止、断线和正常退出时，只恢复仍归当前会话拥有的变更，避免覆盖用户之后的操作。窗口关闭可以进入托盘；托盘退出必须真正停止核心并退出进程。

硬杀进程、断电等情形无法保证执行清理，因此自动静音不是无条件恢复承诺。第一版默认关闭该开关。

## 可验证边界

协议解析、认证数学、PCM 转换、重采样、静音所有权、ABI 输入边界通过自动化测试验证。Windows CI 负责编译原生 UI 和平台代码。真实 HomePod 的固件、密码开关、访问控制、休眠、断网与立体声组合必须用实际设备验证，不能由编译成功替代。
