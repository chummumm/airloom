# Airloom 架构

Airloom 是从零实现的 Windows 桌面项目。它使用 Windows 自带的 WASAPI 采集已有输出端点，使用独立实现的 AirPlay 发送器发送音频，原生界面使用 WinUI 3 / C++/WinRT。它不安装自定义声卡驱动，也不会新增系统播放设备。

## 三个模块

| 模块 | 负责的内容 | 不向上层暴露的细节 |
| --- | --- | --- |
| `airloom-capture` | 已有音频端点枚举、采集、格式转换、重采样、可选本机静音、凭据存储 | COM 生命周期、WASAPI 缓冲区、设备格式、线程归属 |
| `airloom-airplay` | mDNS 发现、认证、RTSP 控制、音频编码与发送、时钟与重传 | SRP/TLV/加密帧、协议序列、网络包 |
| `airloom-core` | 多设备选择、各设备连接状态、共享采集与分发、取消、恢复、可观测指标 | 音频调度、任务代次、各设备密码生命周期 |

`native/Airloom` 是真正的 WinUI 3 应用。它通过一个很小的 UTF-8 JSON C ABI 与 `airloom_core.dll` 交换命令和快照；GUI 线程不执行网络连接或音频采集。ABI 见 [`include/airloom.h`](../include/airloom.h)。

## 声音与时序

Windows 采集在线程内部转换成 44.1 kHz 双声道浮点 PCM。所有所选设备共用一次采集；核心把每个完整音频块量化成 16-bit PCM，以共享数据分别交给各设备独立的有界队列。每个 Sender 在自己的任务中控制发送节奏，既不争抢采集数据，也不让慢设备阻塞其他设备。PTP 网络端口按本地接口共用，各接收端的时钟跟随状态仍然独立。

核心按单调时间线每 10 ms 产生 441 帧，定时器只负责唤醒。延迟唤醒按应有的块数补齐，每次最多补 8 块；超过 200 ms 的停顿丢弃旧采集积压后恢复。各设备最多排队 16 个块，超过 200 ms 的待发送块不再进入 Sender；队列拥塞或发送失败只触发该设备的恢复流程。多个设备可以同时播放，但这里不承诺原生立体声组或采样级多房间同步。

界面波形和左右电平展示输出 PCM，空闲时为平线。用户主动触发的 3 秒测试音在输出阶段加入并明确标记；独立的 `capture` 指标始终报告实际 Windows 端点、采集帧数和源信号，不会把测试音或补入的静音当成采集成功。

声音捕获支持已有端点的共享模式播放，以及明确选择的应用进程树。两种来源都使用 Windows 自带的 loopback 接口。WASAPI loopback 不等于路由：采集不会自动移除本机声音。端点模式的静音是用户可选操作，不默认开启；具体端点的静音前采集行为必须实机验证，应用模式不修改端点静音。

切换来源或来源类型时，采集任务与发送任务分别管理：只停止旧 Windows 采集、清掉本地旧来源音频并建立新采集，已有接收端会话和发送时间线继续。切换期间可能短暂静音。指定应用未选定、进程退出或来源暂不可用时，继续给现有发送队列提供零样本，不回退到其他应用或系统声音；用户选到有效来源后继续发送其音频。

## 连接与密码

每台设备分别维护空闲、连接中、等待认证、发送中、重连和错误状态。只要仍有设备发送，全局状态保持 `streaming`，另一台设备可以同时等待认证或显示错误。发送状态表示链路已建立，不是设备已经发出可听声音的测量结果；共享采集在切换或等待选择时可以处于静音等待状态。手动重新发现保留活跃服务订阅、已知设备及发送会话，更换声源也不重启接收端连接。明确设备移除、发送故障和原生组合成员关系变化仍按对应故障流程处理。

设备密码、配对码和长期配对凭据是不同的数据，分别绑定设备身份。认证按设备顺序处理，弹窗请求编号和连接任务代次用于拒绝过期结果；第二台设备认证或连接失败不会停止第一台。凭据失败返回认证界面，不能无限自动重试。密码不进入快照、错误诊断、日志或仓库。只有用户勾选“在此电脑记住”时，才持久化到 Windows 当前用户的凭据存储；忘记凭据只删除对应设备的记录。

## 设备音量

连接读取接收端 `/info` 中有效的 `initialVolume`，不因启动或建立会话发送默认音量，也不在本地持久化设备音量。核心按已选设备和组合成员聚合读数；全部可用时 `volume_known` 为真，读数差异达到 0.5 个百分点时 `volume_mixed` 为真。界面分别显示百分比、“不同”或未读齐时的“—”；混合状态的滑块参考首个已选成员读数。

只有明确的 `set_volume` 操作才设置当前所选目标。原生界面在没有已连接或正在连接目标时禁用音量，避免生成供未来设备继承的本地默认值；已连接且读数未知时仍允许手动设置。数值反馈继续使用 180 ms 合并和确认保护，传入的设备快照在渲染期间更新控件，不反向产生调节命令。

## 原生设置与更新

`native/Airloom` 管理主题、波形显示、托盘、可选开机启动和设备可见性；这些偏好保存在当前用户设置中，不含密码。隐藏设备会先取消该设备的选择，恢复显示不会自动连接；设备发现也不会自动选中新目标。开机启动只进入托盘，不自动采集、连接或静音。

更新服务独立于 Rust 音频引擎，在原生后台任务中检查发布版本、下载并核对安装包 SHA-256。用户发起安装后，界面正常停止核心并退出，`native/Updater` 中的独立助手等待主进程结束，再安装、重新打开应用并清理下载内容。

## 静音恢复与退出

捕获模块记录自己设置的端点静音变更，监听外部修改。最后一条发送链路停止、整体断线、切换声源或正常退出时，只恢复仍归当前会话拥有的变更，避免覆盖用户之后的操作。停止其中一台设备时，其余设备继续使用共享采集。窗口关闭可以进入托盘；托盘退出必须真正停止核心并退出进程。

硬杀进程、断电等情形无法保证执行清理，因此自动静音不是无条件恢复承诺。该开关默认关闭。

## 可验证边界

协议解析、认证数学、PCM 转换、重采样、静音所有权、广播分发、故障隔离、过期认证、单调调度和 ABI 输入边界通过自动化测试验证。Windows CI 负责编译原生 UI 和平台代码。真实 HomePod 的固件、密码开关、访问控制、休眠、断网与多设备播放必须用实际设备验证，不能由编译成功替代。
